# Contributing — как ведётся работа над Easy-screenshot-tool

База — CONTRIBUTING.md репозитория Investment-accounting-system (правила владельца), адаптирована
под этот проект: C++17 / Win32 / Direct2D, один исполнитель, доска = GitHub Projects.

## 1. Доска — единственный носитель работы

- Карточка = GitHub issue. Доска = проект «Easy-screenshot-tool». Веха (milestone) = релиз.
- Статус карточки обязан отражать фактический прогресс. Колонки Status на доске этого репозитория:
  `Todo → In Progress → Done` (полный набор Design / Development / Test / In review через API этим
  токеном не создаётся — дополнительные колонки заводит только владелец доски в UI).
- Взял задачу в работу — перевёл карточку в `In Progress`. Точный этап цепочки внутри
  `In Progress` фиксируется меткой: `step:research` → `step:dev` → `step:test` → `step:review` →
  `step:done`.
- В `Done` карточка уходит только после approve reviewer; переводит ведущий, не исполнитель.
  Ведущий `Review → Done` не двигает без решения reviewer.
- Карточка вехи обязана иметь заполненные: Status, milestone, метку приоритета `P0/P1/P2`
  (`P0` — критический путь, `P1` — ценностное ядро релиза, `P2` — вспомогательное) и метку
  этапа `step:research|step:dev|step:test|step:review|step:done`. Пустое поле = карточка не
  готова к работе.
- Отчёт о доске — только после API-сличения реальных значений полей (`python tools/board_sync.py
  report`), а не «создал карточки и всё ок».

## 2. Цепочка приёмки

`designer` (спецификация) → `developer` (реализация) → `tester` (независимые тесты, дефекты) →
`reviewer` (итоговое решение: принять / список блокирующих проблем).

- В любой момент времени работает ровно один исполнитель; параллельные субагенты запрещены.
- Каждая передача содержит: что сделано, как проверено, что осталось, ссылки на файлы и строки.
- Границы: tester не пишет прод-код; developer не пишет тесты и не правит чужие тесты ради зелени;
  reviewer ничего не меняет.
- Задача заводится до начала работы; статус меняется по факту выполнения, не по планам.

## 3. Коммиты и пуши

- Conventional Commits: `type(scope): описание`. Типы: `feat fix docs test chore refactor build perf revert`.
- Коммит + пуш обязателен на каждую закрытую карточку и на каждый завершённый рабочий цикл:
  рабочее дерево не должно жить без коммита дольше одного цикла итераций.
- Сообщение коммита обязано ссылаться на карточку: `(#7)`.
- Коммитить только свои файлы. `git add -A` по грязному дереву запрещён; перед коммитом — `git diff --cached`.
- CRLF-шум вне диффа: `.gitattributes` держит `eol=lf`; массовая перекодировка — отдельным коммитом.
- Артефакты сборки (`build/`) в репозиторий не попадают.

## 4. Что нельзя тащить в репозиторий

- Ассеты и артефакты реверс-инжиниринга чужого ПО (бинарники, извлечённые ресурсы, снимки чужого
  интерфейса, дампы строк). Паритет фиксируется только как наблюдение текстом в `docs/RESEARCH-TOOLS.md`.
- Одноразовые диагностические скрипты и логи прогонов: они живут в рабочей папке вне репо. В git
  попадают только версионированные инструменты (`tools/`, `tests/`) и артефакты приёмки
  (`docs/icons/*.png`, `docs/RESEARCH-TOOLS.md`).
- Секреты (токены, ключи, содержимое `.env`) — нигде: ни в коммитах, ни в карточках, ни в памяти.

## 5. Тесты против показухи

- Проверка проверяет поведение, а не геометрию. «Контроль нарисован в нужном слоте» не доказывает,
  что иконка читаема, что текст вводится кликом, что Ctrl+Z отменяет кроп, что Save и Copy делают
  нужное.
- UI-правки проверяются глазами всегда, без исключений: зелёные автотесты UI-пункт не закрывают.
  К каждой UI-правке — снимок состояния (`docs/icons/`) и вердикт глазами.
- Регрессия на дефект = тест на поведение. Тест обязан падать красным на намеренно сломанной сборке
  (доказательство RED), прежде чем фикс заявлен.
- Агентские пробы (временные скрипты, print-наблюдения, прокликивание чужого UI) — agent-time: не
  коммитятся и не становятся регрессионными тестами.

## 6. Живая проверка до «исправлено»

Прежде чем писать «исправлено» или закрывать карточку:

1. воспроизвести симптом на реальной сборке (и показать, что он был до правки);
2. проверить правку тем же сценарием на этой же сборке;
3. показать артефакт в карточке: кадр экрана, вывод автотеста или созданный файл.

Автотест, который проверяет только вызовы собственных функций, симптом не ловит.

## 7. Конвейер вехи (веха = релиз)

1. Объём вехи зафиксирован карточками и milestone.
2. Чеклист приёмки (`docs/ACCEPTANCE.md`) актуализирован до начала разработки.
3. Дизайнерская волна (спецификация) → все карточки вехи в Development.
4. Разработка пакетом (карточки подряд, без возврата к уже сданным) → пуш → карточки в Test.
5. Тестирование одной волной: годные → In review; дефекты списком (файл:строка, факт/ожидание,
   как воспроизвести) → обратно в Development.
6. Пакет фиксов, затем одна повторная тест-волна только по дефектным карточкам.
7. Один reviewer-проход по всему диффу.
8. Ручной прогон чеклиста глазами — никогда не пропускается.
9. Релиз делает один скрипт: `python3 tools/release.py v0.x.y --milestone "<название вехи>"` —
   экспорт релизного коммита, сборка артефактов на собирающей машине (`build.ps1 -Selftest`, без
   `SELFTEST PASSED` релиз не состоится), версионированные имена `ShotMvp-<версия>.exe` /
   `ShotMvp_console-<версия>.exe`, тег, размер и SHA-256 в теле релиза, закрытие milestone,
   карточки в Done. Ручное «забыл прикрепить» этим шагом исключается (карточка #23).

Ограничители: максимум две тест-волны и один ревью-проход на веху. Третья волна — только по
отдельному решению владельца.

## 8. Чеклист приёмки (`docs/ACCEPTANCE.md`)

- Формат пункта: `кто / где (экран) / действие (клики, ввод, выбор) → что видно глазами`.
- Запрещено: имена функций и модулей, флаги тестов, grep-контракты, «проверить лог/код».
- Владелец файла — tester; файл всегда актуален; разработчик проверяет свою работу по нему же.
- Метрика — escape rate: дефекты, найденные проверками до релиза, против найденных владельцем
  после релиза (цель ≤ 2). Каждый дефект владельца порождает пункт чеклиста + регрессионный тест.

## 9. Сборка и проверки

- Сборка: `pwsh build.ps1` (полная команда: `windres -J rc -i src/app.rc -O coff -o
  build/app_res.o -I src`, затем `g++ -std=c++17 -O2 -municode -DUNICODE -D_UNICODE
  src/main.cpp build/app_res.o -o build/ShotMvp.exe -lgdi32 -luser32 -lshell32 -lole32 -ld2d1
  -ldwrite -ldwmapi -lgdiplus`). Манифест DPI — ресурс из `src/app.rc` + `src/app.manifest`,
  а не правка готового exe. Перед сборкой снять процессы `ShotMvp*`.
- `python tests/stage1_states.py` — приёмка панели: геометрия, состояния, клики, полоса статуса,
  сквозной сценарий (exit 0 = PASS).
- `python tests/stage2_behaviour.py` — поведение: текст кликом и с клавиатуры, подложки, кадрирование
  и его отмена, копирование/сохранение в обоих режимах вывода (карточки #5 #6 #7 #8).
- `python tests/stage3_open_png.py` — открытие готового файла (`ShotMvp.exe file.png`),
  побайтовая целостность «открыл → сохранил» и вес полного кадра (карточки #16 #17).
- `python tests/stage4_unsaved.py` — учёт несохранённых правок: «Сохранить» неактивен пока правок нет,
  подпись группы вывода, три ответа на закрытие «Сохранить / Не сохранять / Отмена» (карточка #22).
- `python tests/stage5_layout_resize.py` — матрица из 12 размеров окна и инварианты раскладки
  (пилюля внутри клиента, полоса статуса под пилюлей, ни одного контрола вне пилюли, то же число
  контролов на любом размере, клик активирует нарисованный контрол, пол окна задан контентом):
  карточка #24, инварианты docs/WIN11-UI-GUIDE.md §20.
- `python tests/dpi_verify.py` — оверлей закрывает весь физический экран, окно редактора
  признаётся Windows per-monitor DPI aware, выделение до правого нижнего угла сохраняется целиком.
- `python tools/icon_sheet.py build/icon-sheet.png` — увеличенный лист иконок: читаемость глифов
  проверяется по нему, а не по общему скриншоту.
- Все Python-зонды обязаны быть per-monitor DPI aware (`ui_probe.make_probe_dpi_aware()`); метрики
  снимаются по фактическим пикселям экрана (`SM_CXSCREEN`), а не по виртуальному экрану.

## 10. Память

Ключевые решения, договорённости владельца, причины отказов — в Mnemosyne (`scope: global`) до
компакции контекста. Секреты не записываются и не показываются в ответах.
