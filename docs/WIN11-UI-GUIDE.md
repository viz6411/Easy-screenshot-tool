# WIN11-UI-GUIDE — как делают UI в приложениях Windows 11 и что из этого берём

Собрано 2026-11-16 под карточку #24 (раскладка редактора ломается при изменении размера окна).
Это рабочий документ: каждая rule → конкретное место в коде и измеримый признак для харнеса.

## 1. Стек: остаёмся на Win32 + Direct2D/DirectWrite, берём практики Fluent

Проверено на приёме, что доступно на машине сборки: MinGW-w64 `g++` 16.1 + `windres`, Python 3.11,
`segmdl2.ttf` (Segoe MDL2 Assets) и семейство `segoeui*.ttf`; **Segoe Fluent Icons на машине нет**
(`ls /mnt/c/Windows/Fonts` → только `segmdl2.ttf`). WinUI 3 / Windows App SDK требует MSVC и
C++/WinRT (MinGW этого не собирает), Qt/.NET — тянут в продукт зависимость ради тулбара и ломают
то, ради чего приложение существует: слоистое оверлейное окно, глобальный хоткей, трей, один exe без
рантайма. Microsoft для нативных приложений прямо рекомендует тот же путь: манифест PMv2 + своя
пересобираемая раскладка + Fluent-метрики в собственном рисовании.

Решение: стек не меняем; меняем **архитектуру раскладки** и доводим метрики/поведение до Fluent.

## 2. DPI: Per-Monitor V2 и «раскладку можно пересчитать в любой момент»

Источник: High DPI Desktop Application Development on Windows, WM_DPICHANGED (learn.microsoft.com),
«Writing Win32 apps like it's 2020» (building.enlyze.com, part 3).

- R1. Процесс объявлен per-monitor V2 через манифест (у нас `src/app.manifest`, компилируется
  `windres`) — не `SetProcessDPIAware()` и не V1: V1 «очень ограничен», рекомендуют V2.
- R2. Логика раскладки вынесена из инициализации в переиспользуемую функцию, которую можно вызвать
  заново на `WM_DPICHANGED`, `WM_SIZE` и смене контента. У нас это `layout()`; он обязан быть единственным
  источником геометрии (paint и hit-test читают один и тот же вектор слотов).
- R3. На `WM_DPICHANGED` окно ставится в **предложенный Windows прямоугольник** из `lParam`
  (`SetWindowPos`), иначе окно «относительно всего остального» станет в два раза меньше/больше.
  После этого заново грузятся шрифты/текстовые форматы и метрики (у нас `Theme::load(newDpi)` +
  пересоздание `cv_`), и только потом `layout()`.
- R4. DPI окна = последний присланный `WM_DPICHANGED`; ничего не кешируется от старого DPI.
- R5. Не кешировать битмапы, зависящие от DPI, между перерисовками (GDI/D2D-микс: GDI scaling ломает
  D2D-часть). У нас DIB пересоздаётся в `bind_dc()` на каждый `WM_SIZE` — это правильно; так же
  нужно на смену DPI.

## 3. Размер окна: минимум диктует контент, а не «красивое число»

- R6. `WM_GETMINMAXINFO`: нижняя границка окна = минимальная раскладка, которую приложение умеет
  отрисовать без обрезки (по ширине) + требуемая высота (пилюля текущей раскладки + полоса статуса +
  поля). Граница должна **пересчитываться**, потому что минимальная высота зависит от числа строк
  пилюли, а оно зависит от ширины.
- R7. `WM_SIZE`: пересобрать поверхность рисования (новый DIB + `BindDC`, без swap chain) и
  `layout()`. Дорогое (шрифты/глифы) не пересобирать на каждый пиксель перетаскивания — только на
  `WM_EXITSIZEMOVE` (иначе окно «дёргается»).
- R8. Клиентская область — единственная система координат раскладки; ни один контрол не имеет права
  выйти за неё или за свою группу. Проверка инварианта — часть харнеса, а не «на глаз».

## 4. Тулбар: измерил → упаковал в строки → переполнение закрыто

Источник: Fluent 2 Toolbar (fluent2.microsoft.design) — «toolbar grows to fit its parent container but
never wraps onto a second line; where options don't fit use overflow»; CommandBar
`IsDynamicOverflowEnabled` — команды автоматически уходят в overflow-меню при нехватке места;
типичный баг Fluent-приложений — «items extend outside the container instead of moving into overflow»
и горизонтальная прокрутка вместо переполнения.

- R9. Раскладка тулбара = **упаковка групп в N строк** (N ограничено) по фактической ширине клиента,
  а не выбор из заранее заготовленных «уровней», calibrated на один экран. Порядок групп стабилен
  (инструменты → цвет → свойства → история → вывод), разделитель только между группами одной строки.
- R10. Если содержимое не влезает — последовательная деградация, всегда измеримая: сначала убираются
  подписи контролов, потом упаковка в больше строк, потом **overflow** (группа уходит в кнопку
  «ещё» с текстовыми пунктами — Fluent требует подпись в overflow, не только иконку). Горизонтальной
  прокрутки и обрезки не бывает ни при каком размере.
- R11. Минимальная ширина окна = ширина самой широкой группы (plain-вариант) + поля: ровно та граница,
  при которой упаковка в 1 строку ещё возможна хотя бы для одной группы; всё, что уже невозможно,
  запрещено самой системой окон.

## 5. Метрики Fluent (что берём дословно)

- R12. Целевая зона нажатия: Microsoft — 7.5 мм ≈ **40×40 px** (135 PPI, 1.0× plateau); WCAG 2.2 AA —
  минимум 24×24 px. У нас `ctlH` 32 (56 @175 %) плашка и `ctlHit` 40 (70 @175 %) зона — соответствует;
  инвариант харнеса: зона нажатия любого контрола ≥ 40 px при 100 % DPI и масштабируется с DPI.
- R13. spacing ramp 4/8/12/16/20/24 (у нас `s2…s24`), внутри компонента — меньшие спейсеры, между
  компонентами — большие; Fluent прямо предупреждает: спейсеры — инструмент ритма, а не «везде одно и
  то же число».
- R14. Типографика: Segoe UI Variable → при отсутствии Segoe UI; шкала 1,25; подписи не мельче 12 px
  при 100 % DPI; контраст подписного текста ≥ 4.5:1 (у нас `textSecondary` 7.36:1 на пилюле).
- R15. Иконки стандартных команд — из системного icon-шрифта, а не самодельная геометрия:
  Undo `E7A7`, Redo `E7A6`, Save `E74E`, Delete `E74D`, Copy `E8C8`, Open `E7AC`, Zoom `E8A3`,
  Crop `E7A8`. На этой машине доступен `Segoe MDL2 Assets` (Segoe Fluent Icons отсутствует — MS
  помечает MDL2 как доступный, Fluent Icons как рекомендуемый). Правило смешивания: самодельная
  геометрия остаётся только там, где глифа нет (стрелка, овал, маркер, произвольные фигуры), и
  держит тот же слот 24 юнита / штрих 1.6 px, что и глифы.
- R16. Состояния контрола обязательны: normal / hover / pressed / **focus** / disabled. Focus —
  видимый контур с реальным контрастом (WCAG 2.4.11/2.4.13 как базовая планка), не 1 px в цвет фона.
- R17. Клавиатура: у самописных D2D-контролов нет UIA-дерева, значит доступность обеспечивается
  поведением: Tab/стрелки переводят фокус по контролам в порядке групп, Enter/Space активируют,
  Esc отменяет, горячая клавиша дублирует каждую команду, статус полосы проговаривает результат.
  Это единственный честный способ сделать самописный тулбар доступным в Win32.
- R18. Подсказка при наведении (имя команды + горячая клавиша) — Fluent tooltip: появляется с
  задержкой, не перекрывает сам контрол, не появляется для контрола в состоянии disabled.
- R19. Разрушающие подтверждения — системный `TaskDialog` (масштабируется по DPI, кнопки на языке
  системы уже частично закрыто карточкой #22), молча терять пользовательскую работу запрещено.

## 20. Инварианты, которые проверяет харнес (из R1-R19)

1. Все контролы внутри пилюли и внутри клиента (любой размер окна из матрицы).
2. Прямоугольники контролов не пересекаются; зона нажатия ≥ 40 px @100 %.
3. Пилюля и полоса статуса не пересекаются; полоса видна целиком.
4. Минимальный размер окна диктуется контентом: при минимальном размере ничего не обрезано.
5. После `WM_DPICHANGED`-подобной смены масштаба геометрия пересчитана (окно в предложенном
   прямоугольнике, метрики нового DPI) — проверка `tests/dpi_verify.py`.
6. Подписи не выходят за свою группу и не накладываются на соседнюю.
7. Ничего не «уезжает» при перетаскивании границы: после серии `WM_SIZE` инварианты 1-4 снова истинны.

## 21. Что сознательно не берём

- WinUI 3/XAML-остров в окне (нужен MSVC + WindowsAppSDK; ломает единый exe и слоистое окно).
- Готовый Fluent-контрол-фреймворк ради тулбара (зависимость ради 20 кнопок).
- Непрерывный ползунок масштаба, анимации тулбара, светлая тема — вне карточки #24.
