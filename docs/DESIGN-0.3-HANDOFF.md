# DESIGN-0.3-HANDOFF — карточки #13, #14, #15, #22

Документ для разработчика. Все решения приняты, вариантов нет; там, где решение упирается в
владельца, оно вынесено в §10. Проверка каждого состояния — измерением, по правилам
CONTRIBUTING.md («каждое состояние видно на пикселе»).

## 0. Как читать числа

Единица — физические пиксели при 100 % DPI; в скобках то же число при 175 % (×1,75), на каком
экране идёт приёмка 0.3 (2560×1600, per-monitor V2). Token-имена — из `src/theme.h`, они уже
домножены на DPI, в коде писать токены, а не константы.

| токен | 100 % | 175 % | что это |
|---|---|---|---|
| `ctlH` | 32 | 56 | плашка контрола в пилюле |
| `ctlHit` | 40 | 70 | зона нажатия (п.5 приёмки: 70×40 px) |
| `s2 / s4 / s6 / s8 / s12 / s16 / s24` | 2/4/6/8/12/16/24 | 4/7/11/14/21/28/42 | сетка отступов |
| `fsCaption / fsBody / fsH4 / fsH2` | 11/13/16/20 | 19/23/28/35 | шкала шрифта 1,25 |
| `caption_line()` | 14 | 25 | строка подписи (`fsCaption*4/3`) |
| `strokeW` | 1,6 | 2,8 | основной штрих значков |
| `rControl / rPanel / rFloating` | 6/10/12 | 10,5/17,5/21 | радиусы |
| `glyphBox / glyphSize` | 24/20 | 42/35 | поле значка и сам значок |

Разрешённые поверхности и чернила — только существующие (`canvas`, `floating`, `control`,
`controlHover`, `controlPressed`, `accentFill`, `accentGlyph`, `borderSoft` 7 %, `borderStrong`
14 %, `textPrimary/Secondary/Tertiary/Muted`, `focusRing` 30 %). **Новых цвета и токена в 0.3
нет.** Красный `#E42A31` — цвет содержимого аннотации, в интерфейс не входит.

Авторитет в геометрии — `measure_fits()` / `pill_h_for()` (`src/editor.h`), а не числа этого
документа: здесь числа нужны, чтобы принять дельту и понять, что не должно измениться.

## 1. Что меняется в макете окна

### 1.1 Группа инструментов: 6 контролов → 8

Порядок чипов (`tool_caption`, `src/editor.h`): **`Выбор`** (1-й), `Стрелка`, `Текст`,
`Прямоугольник`, `Овал`, `Маркер`, **`Размытие`**, `Кадрирование` (8-й). `Размытие` встаёт перед
`Кадрированием` — тот же порядок, что и в строке A TOOLBAR-SPEC §1. `Копировать`/`Сохранить`
остаются в группе вывода, `Отменить`/`Повторить` — в группе истории.

Ячейка группы остаётся одинаковой по ширине для всех чипов: `tool_cap + 2·s4` с зазором `s6`
(TOOLBAR-SPEC §8: ячейка 153 px, шаг 164 px при 175 %); `tool_cap` не растёт — «Выбор» и
«Размытие» короче «Прямоугольник» (139 px), а значит `tool_cap` остаётся прежним. Считать по
модели TOOLBAR-SPEC §8 (`build_groups` + `row_width` + `pill_width_for`), а не по замеру:

| группа | 0.2 (6 чипов) | 0.3 (8 чипов) |
|---|---|---|
| инструменты | 6·153 + 5·11 = 973 | 8·153 + 7·11 = **1301** |
| цвета (7 свотчей) | 7·56 + 6·4 = 416 | 416 |
| свойства | 3·56 + 2·4 = 176 | 176 |
| история | 2·56 + 4 = 116 | 116 |
| вывод | 2·118 + 11 = 247 | 247 |
| межгрупповые зазоры (39 + 32 + 32 + 32) + отступы пилюли 42 | 383 | 383 |
| **`pill_w_`** | **2105** | **2433** (+328) |

Клиент: `wantClientW = pill_w_ + s24` = 2147 → **2475 px**, окно (рамка 16 px) 2163 → **2491 px**.
Предел экрана 2560 при 175 %: `scrW − 8` = 2552 px окна → **запас 61 px**; проверка уровня
`fit_w_ + 2·s8 ≤ клиент` даёт 2455 ≤ 2475 (запас 20 px). Девятый чип стоит 164 px — уровень
`FIT_LABELS_1ROW` на нём ломается и включается перенос на две строки (§9.2).

Клавиши инструментов привязаны к порядку чипов: `1` = Выбор, `2` = Стрелка, `3` = Текст,
`4` = Прямоугольник, `5` = Овал, `6` = Маркер, `7` = Размытие, `8` = Кадрирование. Это ломает
прежнюю раскладку 0.2 (`1..6`, `7` = «масштаб 100 %»): сброс масштаба переезжает на `0` (§3.4),
`Esc` — на снятие выделения (§2.3). Подсказка по горячим клавишам в полосе статуса обязана
совпадать с новой раскладкой (п.25 приёмки).

### 1.2 Вторая подписная строка в подписанных уровнях

Подписи групп («Цвет», «Толщина»/«Фон»/«Сила»/«Масштаб», «вывод») сейчас рисуются в той же
строке, что подписи контролов, и поэтому могут стоять только там, где подписей контролов нет
(цвет, свойства). Карточке #22 нужна подпись группы вывода — значит строки надо разделить.

`cell_h()` в подписанных уровнях (`FIT_LABELS_1ROW`, `FIT_LABELS_2ROW`):
`ctlH + s4 + caption_line` (50 / 88 px) → **`ctlH + 2·s4 + 2·caption_line` (68 / 120 px)**
(при 175 % числа целые из `Theme::load`: 56 + 14 + 50).
Порядок внутри ячейки сверху вниз: плашка `ctlH`, `s4`, **подпись группы** (`fmtCaption`,
`textSecondary` — как сегодня рисуются «Цвет» и «Толщина», цвет не меняется), `s4`, **подпись
контрола** (`fmtCaption`, `textSecondary` → `textPrimary` при наведении). Разные подписи
различаются местом строки, а не цветом. В безыменных уровнях (`FIT_PLAIN_*`) — без изменений.

Дельта высоты: **+18 px при 100 % (+32 px при 175 %)** на строку. `pill_h_for` (та же формула
дублируется в `build_slots()`, править надо оба места, иначе высота пилюли и позиции рядов
разъедутся): однострочный подписной уровень 110 → **142 px**, двухстрочный 209 → **273 px**;
безыменные уровни не меняются (78 / 145 px). Высота окна: `wantClientH = s12 + pill_h_ + PAD_TOP
+ img.h + PAD_BOTTOM + FOOT_H` = 227 + img.h → **259 + img.h** при 175 %; при снимке во весь
экран окно и так упирается в `scrH − 8`, то есть 32 px нижней кромки снимка уйдут — это следствие,
оно вынесено в §10.1. Ширина от этого не меняется (важно: запас по ширине мал, §9).

### 1.3 Группа свойств: тот же размер, четыре панели

Группа свойств остаётся 3 ячейками `ctlH` с зазором `s2` (100 / 176 px) и **никогда не меняет
ширину**. Меняется только набор слотов внутри (механизм уже есть: `KIND_WIDTH` ↔ `KIND_BACKDROP`
в `build_groups`). Панель выбирается по приоритету:

| условие | панель | подпись группы |
|---|---|---|
| есть выделенный объект | его свойства (§2.4) | `Свойства` |
| инструмент `Размытие` | 3 кнопки силы (§4.2) | `Сила` |
| инструмент `Текст` | 3 состояния подложки (как в 0.2) | `Фон` |
| любой рисующий инструмент, в том числе `Кадрирование` | 3 толщины (как в 0.2) | `Толщина` |
| инструмент `Выбор`, выделения нет | `−` `100 %` `+` (§3) | `По размеру` / `Масштаб` |

Пустой панели свойств не бывает: каждая из перечисленных панелей содержит **ровно 3 контрола** —
так пилюля не меняет ширину при смене инструмента, и групповая подпись всегда есть. Это важно для
реализации: `paint_pill` пропускает групповую подпись, когда `grp_w_[r][g] <= 0` (пустая группа),
то есть панель из 0 слотов потеряла бы и подпись, и смысл.

Отдельной панели кадрирования в 0.3 нет: карточка кадрирования стоит в 0.2 и ни одна из четырёх
карточек 0.3 её не просит, поэтому `Кадрирование` держит панель `Толщина` (кадрирование её не
использует — панель не пустая, но и не обещает ничего лишнего). Панель пропорций и `Готово` — вне
объёма 0.3.

### 1.4 Что не должно измениться

Высота и позиция полосы статуса (`FOOT_H = 2·s6 + caption_line` = 26 / 47 px), зазор
`PAD_BOTTOM` между снимком и полосой (п.25), тип поверхности каждой группы (инструменты и свойства —
плашка `control` с границей `borderSoft`, `CG_TOOL`; история — только яркая обводка на поверхности
пилюли, `CG_PLAIN`; вывод — утопленная ниша `canvas`, `CG_SUNKEN`), порядок групп
`инструменты | цвет | свойства | история | вывод`, пороги уровней — их считает `measure_fits()`
по факту, отдельных констант заводить нельзя. `WM_GETMINMAXINFO` остаётся на `pill_min_`.

## 2. Карточка #13 — правка уже нарисованного

### 2.1 Выбор

Инструмент `Выбор` (чип 1, хоткей `1`, новый значок: контур курсора — замкнутый многоугольник в
поле `glyphBox`, штрих `strokeW`; чернила как у остальных чипов, их выбирает `ui::glyph()`: покой
`accentGlyph`, наведение `textPrimary`; точки в поле 24×24 px при 100 %:
(6,3)-(6,19)-(10,15)-(13,21)-(15,20)-(12,14)-(18,14)-закрыть).

`enum Tool` получает `TOOL_SELECT` первым и `TOOL_BLUR` перед `TOOL_CROP` (массив `tools[6]` в
`on_key` становится `tools[8]`); в `ui::Glyph` добавляется одна позиция `G_SELECT` (растёт
`G_COUNT`, появляется геометрия в `geometry_for`), значок `G_BLUR` для `Размытия` уже есть.
Редактор открывается с `Стрелкой`, как в 0.2: `Выбор` включается чипом или клавишей `1` — сделать
его инструментом по умолчанию означало бы сломать прогон 0.2, который рисует сразу после открытия
окна.

Попадание проверяется в координатах **снимка** (после `imgX()/imgY()`, §3.2) в порядке:
1) объект, чья геометрия попадает в точку с допуском `ctlHit/2` (20 / 35 px) — для фигур с
заливкой и текста с подложкой достаточно попадания в его габарит; 2) ближайший объект, если до
его линии ≤ `ctlHit/2`; 3) ничего — снимается выделение, начинается панорамирование (§3.4).
При пересечении нескольких объектов выбирается нарисованный позже (верхний).

Нового языка попаданий не появляется: `hit(mx, my)` остаётся проверкой слотов пилюли, а для
аннотаций добавляется одна функция `int hit_stroke(int mx, int my)` — перебор `strokes_` с тем же
допуском, возврат индекса объекта или `-1`. Состояние выделения — два поля: `int sel_ = -1` и
`int sel_part_` (`< 0` — двигать объект целиком, `0..7` / `0..1` — какая ручка). Габарит считается
по `Stroke::pts`, для текста — по замеру `cv_.measure(text, fmt)` вместе с подложкой; нового поля
в `Stroke` для габарита нет.

### 2.2 Рамка и ручки

- Рамка = габарит объекта, раздвинутый на `s8` (8 / 14 px): скруглённый прямоугольник радиуса
  2,0 px, штрих **`accentGlyph` 2,0 px** — ровно та же отрисовка, что у рамки кадрирования
  (`cv_.brAccent`, 2,0 px, радиус 2,0), новых поверхностей нет.
- Ручки: **8** (углы и середины сторон габарита) для прямоугольника, овала, маркера и текста;
  **2** (конечные точки `pts.front()` и `pts.back()`) для стрелки; **0** для кадрирования (у него
  своя рамка, она не «выделение»). Маркер — открытая полилиния из многих точек (`on_move` добавляет
  каждую точку), поэтому ручка двигает не точку полилинии, а **масштабирует всю полилинию** относительно
  габарита (координаты округляются). Внешний вид ручки: квадрат 16 px (28 px при 175 %), заполнение
  `floating`, обводка `borderStrong` 1,5 px. Ручка в перетаскивании: заполнение `accentFill`,
  обводка `accentGlyph` 2,0 px. Зона нажатия — квадрат `ctlHit` 40 px (70 px при 175 %) с центром на
  ручке: это контрол, и п.5 приёмки к нему применяется.
- Перемещение: нажатие внутри рамки, кроме ручек → сдвиг всего объекта (все точки `Stroke::pts`).
- Ручка угла меняет ширину и высоту габарита, ручка середины стороны — одну сторону. Для текста
  ручка выбирает **ближайшее из трёх значений кегля** (§2.4), а не произвольный размер: шкала
  шрифта DESIGN.md остаётся единственной. Для стрелки ручка двигает свою конечную точку — это и есть
  «длина и угол стрелки».
- Минимальный размер после изменения ручки: 8×8 px снимка (тот же порог, что у `apply_crop`);
  ближе ручка не пускает, объект не исчезает.

### 2.3 Клавишные команды

| клавиша | есть выделение | выделения нет |
|---|---|---|
| `Del` | удалить выделенный объект (один шаг истории) | откатить последнее действие (прежнее поведение `Del`) |
| `Backspace` | не трогать: сегодня он принимает `WM_CHAR` (код 8) и стирает символ при наборе текста | как сейчас |
| `Esc` | снять выделение | закрыть редактор → §5.4 |
| `Ctrl+Z` / `Ctrl+Y` | работает как раньше; выделение после отката снимается | как раньше |

### 2.4 Свойства выделенного объекта (панель `Свойства`)

Три слота `KIND_WIDTH`, поле `Slot::width` переиспользуется, новых типов контролов нет:

| объект | 3 кнопки | что меняют |
|---|---|---|
| стрелка, маркер, прямоугольник, овал | 2 / 4 / 8 px при 100 % — те же значения, что `widths_` | толщину штриха объекта |
| текст | 13 / 16 / 20 px — `fsBody` / `fsH4` / `fsH2` | кегль текста |

Образец кнопки рисуется существующим кодом `KIND_WIDTH` (горизонтальный штрих толщиной
`(1,5 + w·0,75)·k`): для кегля значением `Slot::width` становится сам кегль, поэтому три кнопки
читаются тремя толщинами — 13 px даёт штрих 11,25 px (19,7 px при 175 %), 20 px даёт 16,5 px
(28,9 px при 175 %), разница ≥ 30 %, монотонность меряется `row_runs` поперёк чипа.

Цвет выделенного объекта меняют свотчи группы цвета (они на той же строке): нажатие свотча при
выделении правит объект, а не только будущие аннотации. Подложка текста — панель `Фон` доступна и
при выделенном тексте.

### 2.5 История

Каждое завершённое действие = **один** `Change`: перетаскивание объекта, перетаскивание ручки
(одно нажатие и отпускание = один шаг, не по шагу на каждое движение мыши), смена толщины/цвета/кегля
из панели, удаление. `Change` уже умеет носить оба конца правки (`st_before`/`st_after` — этим
пользуется кадрирование), и для правки выделения он обязан нести именно списки целиком: сегодня
`do_action(0)` для не-кадрирования делает `strokes_.pop_back()` (последний штрих), а объект может
стоять не последним. Удаление объекта = `Change` с его индексом (`del_index`): откат вставляет штрих
на своё место, повтор — убирает снова. `Ctrl+Z` после правки возвращает объект в прежние координаты;
автотест меряет пиксели до и после (критерий карточки).

## 3. Карточка #14 — масштаб

### 3.1 Три контрола в группе свойств

`−` (ячейка `ctlH`), `%` (ячейка `ctlH`, текст текущего значения — `fmtCaption`, `textPrimary`:
это значение контрола, а не подпись), `+` (ячейка `ctlH`). Значки `−`/`+`: горизонтальная линия
16 px и плюс из двух линий 16 px, штрих `strokeW`, `textPrimary` (новый значок — рисование, не
токен). Нажатие на `%` = 100 %.

Состояния масштаба три: **`По размеру`** (вычисляемый коэффициент, подпись группы `По размеру`),
**`100 %`** (ровно 1,00, подпись `Масштаб`), ручной масштаб (подпись `Масштаб`).

Диапазон **25 % … 400 %**, шаг **10 %** (TOOLBAR-SPEC §4). `−` на 25 % и `+` на 400 % переходят в
`ST_DISABLED`. Шаг = ближайшее кратное 10 % строго больше / строго меньше текущего значения, за
пределом диапазона значение не меняется; стартовое «По размеру» шагу не кратное — первый `+` от
него округляет до ближайшего шага вверх.

Непрерывного регулятора (`[70 %] [−] [===▮===] [+]` из TOOLBAR-SPEC §4) в 0.3 нет: группа свойств
обязана держать 3 ячейки `ctlH` и не менять ширину (§1.3), а регулятор — контрол переменной ширины.
Ползунок масштаба — отдельная работа (§9).

Контролы масштаба видны в панели только когда активен `Выбор` и выделения нет (§1.3): рисующий
инструмент занимает панель своими свойствами. Поэтому проверка п.28 автотестом начинается с клика
по чипу `Выбор` (или клавиши `1`). Клавиши `−`/`+`/`0` (`VK_OEM_MINUS`, `VK_OEM_PLUS`/`VK_ADD`,
`VK_0`) работают при любом инструменте: масштаб не должен зависеть от того, какая панель сейчас
занята.

`zoom_fit = min(1, (canvas_w − 2·s8)/img.w, (canvas_h − 2·s8)/img.h)`, где `canvas_*` — область
между нижней кромкой пилюли и верхней кромкой полосы статуса. При снимке меньше канваса `zoom_fit
= 100 %`, то есть `По размеру` и `100 %` при маленьком снимке совпадают — это допустимо и
проверяется как один и тот же коэффициент 1,00.

### 3.2 Математика отображения

Единственная точка преобразования — `imgX()/imgY()` (`src/editor.h`), к ней добавляется деление
на масштаб:

```
imgX(mx) = clamp((mx - img_org_x_) / zoom_, 0, img_.w - 1)
imgY(my) = clamp((my - img_org_y_) / zoom_, 0, img_.h - 1)
```

Отрисовка: dst-прямоугольник = `img.w·zoom_ × img.h·zoom_`, интерполяция `NEAREST_NEIGHBOR`
(пиксель в пиксель на увеличении — то, что видит пользователь, и то, что попадёт в экспорт).

Зум вокруг точки: при смене `z → z'` с якорем в точке `m` (координаты окна из сообщения мыши):
`org' = m − (m − org)·z'/z`, затем org зажимается так, чтобы центр изображения остался внутри
канваса. Это даёт и колесо, и кнопки `−`/`+` (якорь кнопок — центр канваса).

**Важно для автотеста:** точка якоря берётся из `lParam` сообщения (`WM_MOUSEWHEEL` — экранные
координаты → `ScreenToClient`), `GetCursorPos` не использовать: тест постит сообщения, настоящий
курсор не двигается (§7).

Всё, что переводится из пространства снимка в экран, умножается на `zoom_`: координаты штрихов в
`paint_stroke`, рамка кадрирования (`crop_a_`/`crop_b_` + `img_org_*`), рамка выделения и ручки
(#13). Помощники — `to_screen(POINT)` и `img_len(int)`, а не умножение в каждом месте отдельно.

### 3.3 Что масштаб не трогает

Размер окна, текст размера снимка в полосе статуса, размеры сохраняемого файла, координаты
аннотаций (они хранятся в пикселях снимка), толщина штриха аннотации в exported-пикселях (на
экране она растёт вместе с масштабом — WYSIWYG). Масштаб **не делает документ грязным** (§5.1).

`ensure_image_visible()` (окно растёт, чтобы снимок влез целиком — путь отмены кадрирования) в 0.3
работает только в состоянии «По размеру»: при ручном масштабе окно не меняется ни после какого
`Ctrl+Z`/`Ctrl+Y`. `zoom_fit` пересчитывается при каждой смене размера документа (кадрирование,
откат кадрирования) и `zoom_` зажимается в новый диапазон.

### 3.4 Как попасть в состояние

| переход | чем |
|---|---|
| −10 % | `−` или колесо вниз или клавиша `-` |
| +10 % | `+` или колесо вверх или клавиша `+` (один щелчок колеса = один шаг 10 %) |
| ровно 100 % | клик по `%` или клавиша `0` (было `7`) |
| по размеру | клик по `%`: из любого ручного значения → `100 %`; повторный клик при `100 %` → `По размеру` (если `zoom_fit = 100 %`, оба состояния дают коэффициент 1,00) |
| панорамирование | перетаскивание инструментом `Выбор` по канвасу, где объекта нет под курсором |

Колесо = масштаб (п.8 DESIGN.md), полос прокрутки в 0.3 нет. Клавиши `0`, `-`, `+` и `1..8`
работают только вне ввода текста (`text_edit_`): набираемый текст не должен терять ни одного
символа — та же отговорка, что уже стоит для `1..6` в `on_key`.

## 4. Карточка #15 — размытие/пикселизация одной силой

### 4.1 Инструмент и жест

Чип `Размытие` (7-й по счёту, хоткей `7`, значок `G_BLUR` уже есть в `src/ui_draw.h`). Жест:
нажатие → перетаскивание → отпускание по области снимка. Во время перетаскивания: рамка как у
кадрирования (2,0 px `accentGlyph`, радиус 2,0) + заполнение внутри `accentFill` (24 %). Живого
размытия во время перетаскивания нет (бюджет кадра): знак готовящейся области — заливка и рамка.

Порог области: **8×8 px снимка** (тот же, что у `apply_crop`); меньше — эффект не применяется, в
полосу статуса идёт `status_msg_ = L"область слишком мала"` с `status_bad_ = true` — тот же канал,
что у `Не удалось скопировать` (правая часть полосы, чернила `accentGlyph`), и живёт оно до
следующего сообщения.

### 4.2 Сила = один параметр

Три кнопки панели `Сила` (те же 3 ячейки `ctlH`, поле `Slot::width` = размер блока):
**8 / 16 / 32 px снимка**, по умолчанию 16. Значок кнопки — мозаика 2×2 / 3×3 / 4×4 заполненных
квадратов в поле `glyphSize` (20 / 35 px), чернила `textPrimary` (≥ 8:1 и на `control`, и на
`accentFill`; монотонно: чем крупнее блок, тем сильнее).
Выбранная кнопка — `ST_ACTIVE` в своей группе поверхности (`CG_TOOL`, как у выбранных толщин 0.2):
заполнение `accentFill`, обводка `accentGlyph` 1,5 px; в покое — заполнение `control`, обводка
`borderSoft` 1,0 px.

Эффект: **мозаика с усреднением в блоке** (box average) — один проход O(площадь), один параметр
содержит и «размытие», и «пикселизацию», как разрешает граница карточки. Сила 8 → блоки 8 px,
16 → 16 px, 32 → 32 px.

### 4.3 Применение и откат

Применение **разрушающее для буфера снимка** (`img_`), как кадрирование: на отпускании блок
пересчитывается, в историю кладётся один `Change` с новым полем `is_filter` и `img_before = img_`
(полная копия снимка уже есть в механизме `apply_crop`, нового не писать). В `do_action` ветка
`is_filter` совпадает с веткой `is_crop` (поменять `img_`, вызвать `refresh_image_bitmap()`), только
списки штрихов не трогать и `ensure_image_visible()` не звать (размер документа не меняется).
`Ctrl+Z` возвращает исходные пиксели области, `Ctrl+Y` — размытие обратно. Размытая область **не
выделяется** инструментом `Выбор` (она стала частью снимка) — граница карточки #13 про аннотации,
это согласуется.

Экспорт и копия в буфер получают уже размытый `img_` без отдельного кода; размер файла не
меняется. Повторное наложение силы на ту же область = второй проход (допустимо).

| loading | нет: один проход по области обязан уложиться в бюджет кадра PLAN §2 (≤ 150 мс), отдельного состояния «ждём» нет | время кадра в тесте |

## 5. Карточка #22 — несохранённые правки, вопрос при закрытии, неактивный «Сохранить»

### 5.1 Учёт (`dirty_`)

`dirty_ = true` на первом из: завершённый штрих, коммит текста, удаление объекта, перемещение или
правка выделенного, смена цвета/толщины/силы/подложки **выделенного** объекта, применение
кадрирования, применение размытия, `Ctrl+Z`/`Ctrl+Y` (откат — тоже правка результата).
`dirty_ = false` после **успешного** «Копировать» или **успешного** «Сохранить» (файл лег на диск
/ DIB лёг в буфер). Отменённое окно сохранения и ошибка записи `dirty_` не сбрасывают.
Масштаб и панорамирование `dirty_` не ставят. Прерванный жест (меньше 2 точек, несостоявшееся
кадрирование) — не ставит.

Правило, из которого нельзя сделать исключение: признак может **излишне** предупредить (правка и
откат к исходному снимку всё ещё дают «есть несохранённые правки»), но никогда не молчит, когда
правка есть.

`dirty_` — не то же, что `produced_` («в этой сессии был хотя бы один вывод», он кормит тост в
`src/main.cpp`): `dirty_` живёт между выводами и сбрасывается каждым успешным, `produced_` — до
конца сессии.

### 5.2 Индикатор

Подпись группы вывода — верхняя из двух подписных строк новой подписной части ячейки (§1.2): тот же
формат `fmtCaption` и тот же цвет `textSecondary`, что у групповых подписей «Цвет» и «Толщина».

| `dirty_` | текст | чернила | контраст на `floating` |
|---|---|---|---|
| true | `есть несохранённые правки` | `textPrimary` | 13,51:1 |
| false | `нет несохранённых правок` | `textSecondary` | 7,36:1 |

`textTertiary` для этой строки не используется: на `floating` это 4,27:1 — ниже AA для текста
размером `fsCaption` (19 px при 175 %).

Обе строки ≈ 230 px при 175 % (оценка по долям шрифта Segoe UI 19 px, ±10 %) влезают в ширину
группы вывода 247 px (модель TOOLBAR-SPEC §8: 2 слота × (`out_cap + 2·s4` = 118) + зазор `s6`).
Запас 10…30 px — подпись обязана рисоваться в одном ink-ряде без переноса: если `cv_.measure()`
даст больше 247 px, это решение владельца (§9.7), а не правка «на глаз». Новой поверхности и роста
ширины нет — растёт только высота ячейки (§1.2), потому что в этой группе групповая подпись раньше
не рисовалась вовсе (были только подписи слотов «Копировать»/«Сохранить»).

### 5.3 Неактивный «Сохранить»

При `dirty_ = false` слот «Сохранить» рисуется `ST_DISABLED`. Сегодня в `ui::control()` для
`CG_SUNKEN` ветки `ST_DISABLED` нет: ниша сохраняет обводку `borderSoft`, и неактивный «Сохранить»
отличается от активного только приглушённым глифом. **Правка:** в `CG_SUNKEN` добавить
`ST_DISABLED → no_border = true` — тот же язык, что у неактивной истории (`CG_PLAIN` +
`ST_DISABLED` = заполнение `canvas` без границы, TOOLBAR-SPEC §8.5). Заполнение (`canvas`), глиф
(`textMuted`) и подпись (`textSecondary`) остаются как есть.

Измеримые признаки: `outline_length(Save)` — активный ≥ 40 (обводка ниши по всей высоте чипа),
неактивный ≤ 3 (дырка); плюс смена чернил подписи группы вывода (§5.2, ink ≈ 239 против ≈ 178).
«Копировать» активно всегда (вывод в буфер имеет смысл и без правок). `Ctrl+S` при `dirty_ = false`
не делает ничего — клавиша и кнопка не расходятся.

Контраст неактивного состояния: WCAG 1.4.3/1.4.11 не требуют контраста от неактивного контрола, и
`textMuted` здесь остаётся знаком «дырки», а не текстом, который надо читать; активный «Сохранить»
— глиф `textPrimary` (14,8:1 на `canvas`) и подпись `textSecondary` (7,36:1 на `floating`).

### 5.4 Вопрос при закрытии

Закрытие = крестик окна (`WM_CLOSE`) или `Esc` (при отсутствии выделения и редактируемого текста
`Esc` постит `WM_CLOSE` своему окну вместо `PostQuitMessage` — один путь на все закрытия).

Если `dirty_ = true` — модальный **TaskDialog** (`TaskDialogIndirect`, родитель = окно редактора,
класс окна `#32770`, кнопки — обычные `Button`, доступны тесту через `BM_CLICK`):

| элемент | текст |
|---|---|
| заголовок | `Закрыть редактор?` |
| основной текст | `Есть несохранённые правки. Сохранить их перед закрытием?` |
| кнопка 1 (ID 100) | `Сохранить` |
| кнопка 2 (ID 101) | `Не сохранять` |
| кнопка 3 (ID 102, фокус по умолчанию) | `Отмена` |

Требование к сборке: в `src/app.manifest` добавить зависимость `Microsoft.Windows.Common-Controls`
version 6.0.0.0 (publicKeyToken 6595b64144ccf1df) — без comctl32 v6 `TaskDialogIndirect` не
существует. Строки задаёт приложение (как остальные), не ОС.

Поведение (`case WM_CLOSE` в `on_msg` — сегодня его нет, окно закрывается через `WM_DESTROY →
PostQuitMessage`; `Esc` ведёт себя так же, как крестик): если `dirty_ = true` — диалог; «Отмена» →
возврат из обработчика, окно живо; «Сохранить» или «Не сохранять» → `DestroyWindow(hwnd_)` и прежний
`WM_DESTROY → PostQuitMessage(0)`.

- `Сохранить` → тот же путь, что кнопка «Сохранить» (`do_action(3)` → `save_fn_`): п.23/п.24 — окно
  папки при первом сохранении, окно «Сохранить как» при `save_ask=1` → файл появился → редактор
  закрыт; окно отменено или запись не удалась → **редактор остаётся открытым**, в полосе статуса
  `Сохранение отменено` / `Не удалось сохранить: <путь>` (`accentGlyph` — единственное исключение
  для акцента, TOOLBAR-SPEC §5 п.5).
- `Не сохранять` → редактор закрыт, на диске ничего нового. Тоста «Capture discarded - nothing was
  saved.» после этого ответа нет: вопрос сказал ровно то же самое до закрытия. Правило TOOLBAR-SPEC
  §5 п.6 продолжает работать там, где вопроса не было (нет правок → тост есть) — для этого `Editor`
  отдаёт в `main.cpp` один флаг (`discard_confirmed()`), и условие `if (!ed.run(img))` в `src/main.cpp`
  становится `if (!ed.run(img) && !ed.discard_confirmed())`.
- `Отмена` → редактор открыт, правки и выделение на месте.
- `dirty_ = false` → вопроса нет, закрытие молча (тост остаётся).

## 7. Что должно уметь измерять покрытие (`tests/ui_probe.py`)

Вход 0.3 остаётся тем же, что и в 0.2: постимые сообщения окну (`WM_MOUSEMOVE`/`BUTTONDOWN`/
`BUTTONUP`/`KEY`/`CHAR`), кадр через `PrintWindow`, диалоги — `BM_CLICK` по их кнопкам
(`press_dialog_button` по подписи), результат проверок по диску и полосе статуса. Физические мышь и
клавиатура не используются (карточка #12).

Закрытие редактора в прогоне — пост `VK_ESCAPE` (`press_key`), а не крестик окна: крестик лежит в
неклиентской зоне, и `PostMessageW` даёт туда `WM_NCLBUTTONDOWN`, а не `WM_CLOSE`; `Esc` в 0.3
ведёт себя точно так же, как крестик (§5.4), поэтому проверка та же самая.

Новые помощники (по одному на каждый новый знак, все на уже готовых `col_runs`/`row_runs`):

1. `post_wheel(hwnd, x, y, up)` — пост `WM_MOUSEWHEEL`: `wParam = (±120 << 16) | 0x0001`
   (дельта — в старшем слове `wParam`, константы `MK_WHEEL` не существует), `lParam` — экранные
   координаты точки, в которой «крутят» (`ClientToScreen` от клиентской). В `on_msg` появится
   `case WM_MOUSEWHEEL`, читающий `GET_WHEEL_DELTA_WPARAM(wParam)` и `ScreenToClient(lParam)`;
   настоящий курсор не двигается.
2. `accent_rect(fr, band)` → `[x0,y0,x1,y1]` или `None` — замкнутый контур из 4 прогонов цвета
   акцента. Знак рамки выделения, рамки кадрирования и предпросмотра размытия. Акцент в тесте надо
   калибровать в начале прогона (взять заполнение активного чипа инструмента): `ACCENT_FILL`
   константой в `tests/ui_probe.py` задан один цвет, а рамка выделения, заливка предпросмотра и
   ручка в перетаскивании живут на системном акценте машины, где идёт прогон.
3. `handle_squares(fr, rect)` → список центров — квадраты `floating` с обводкой `borderStrong`
   ≥ 12 px в углу/середине стороны рамки. Знак «8 ручек на месте» и «у стрелки 2 ручки».
4. `shot_bbox(fr, bg)` → `[x0,y0,x1,y1]` или `None` — габарит блока пикселей фикстуры (цвет
   `bg` ± 8) внутри канваса; `zoom_ratio(fr, img_w) = shot_bbox.w / (img_w × 1,75)`. Знак
   состояния масштаба без распознавания текста. `content_bbox` для этого не годится: он требует,
   чтобы снимок закрывал ≥ 25 % высоты канваса (его правило `band // 2 · 0.5`), а при 25…50 %
   масштаба фикстура ниже — helper вернёт `None`.
5. `local_variance(fr, rect)` → средняя дисперсия по окнам 8×8 внутри прямоугольника — знак
   «размытие применено / не применено» и монотонности силы.
6. `caption_ink(fr, group_x0, group_x1, band_y0, band_y1)` → средняя луминанса ink подписной
   строки группы: `dirty_` при ≥ 210 (ink ≈ 239 у `textPrimary`), чисто при 160…190 (ink ≈ 178 у
   `textSecondary`) — знак `dirty_` без распознавания текста.
7. `glyph_ink(fr, box)` → максимальная луминанса внутри центрального квадрата чипа: активный
   «Сохранить» ≥ 200 (`textPrimary`), неактивный ≤ 100 (`textMuted`) — второй, кроме
   `outline_length`, знак неактивности в нише, где заполнение одинаковое и в покое, и в
   неактивности (`canvas`). Для `−`/`+` на краях диапазона достаточно `dominant_fill`: у активной
   ячейки группы свойств заполнение `control`, у `ST_DISABLED` — `canvas` (ветка `ST_DISABLED` в
   `CG_TOOL`), обводка при этом остаётся.

Что в существующем покрытии ломает новый макет и правится вместе с 0.3:

- `find_pill(fr, max_row=220)` и `CHIP_TOP/CHIP_BOTTOM = 8/70` — константы одного ряда плашек.
  После §1.2 ряд стал выше (120 px плашка+две подписи при 175 %), а при двухстрочном уровне пилюля
  занимает 273 px: `max_row` поднимается до 340, `CHIP_TOP/CHIP_BOTTOM` применяются к каждому
  ряду отдельно (второй ряд смещён на высоту первого: `+120 + s6`), `group_separators` и
  `dominant_state` вызываются по разу на ряд.
- Геометрические ожидания переснимаются замером, а не правкой констант: `measure_fits()` даёт
  новые `fit_w_`, тест обязан сравнивать `pill['w']` с шириной клиента (пороги уровня в коде уже
  измеренные, новых констант не появляется).

есть обводка» (`outline_length`) остаётся только для активного состояния.

## 9. Долг 0.3, который остаётся записанным

1. Рамка выделения и рамка кадрирования рисуются одинаково (2,0 px `accentGlyph`); различить их
   можно только по ручкам и подписи панели. Отдельный язык для рамки выделения — отдельная
   карточка.
2. Запас ширины пилюли при 175 % на экране 2560 после 0.3: **61 px окна** (окно 2491 px против
   предела `scrW − 8` = 2552 px). Девятый чип в группе инструментов стоит 164 px — однострочный
   подписной уровень на нём ломается, и дальше только перенос на вторую строку (уровень
   `FIT_LABELS_2ROW`, пилюля 1343 × 273 px).
3. `dirty_` не умеет различать «правка и откат к исходному снимку» → возможен лишний вопрос.
   Точный учёт = сравнение документа с эталоном вывода, в 0.3 сознательно не делается.
4. Размытие разрушает пиксели снимка: выделение и правка размытой области невозможны, откат только
   `Ctrl+Z`; глубина истории ограничена памятью (каждый `Change` носит копию снимка) — в 0.2 уже
   так же.
5. Приёмочные пункты 23 и 24 (первое «Сохранить», «Сохранить» при `save_ask=1`) теперь требуют
   правки до нажатия: при `dirty_ = false` «Сохранить» неактивен. В прогоне 0.3 перед ними должна
   быть хотя бы одна стрелка.
6. Раскладка клавиш инструментов меняется целиком (`1..6` → `1..8`, Кадрирование с `6` на `8`,
   сброс масштаба с `7` на `0`). Настраиваемых клавиш в 0.3 нет — они в этапе 5 по docs/PLAN.md
   (окно настроек); до этого раскладка фиксированная, и текст подсказки в полосе статуса обязан
   ей соответствовать (сегодня в `paint()` подсказка начинается со слова `1-6`).

7. Подпись группы вывода («есть несохранённые правки», ≈ 230 px по оценке долей шрифта) влезает в
   группу 247 px с запасом 10…30 px. Если замер `cv_.measure()` даст больше — нужен либо более
   короткий текст (против буквы п.27), либо третья подписная строка в группе вывода; решение
   владельца (§10.3), а не реализационная импровизация.

8. Непрерывный регулятор масштаба из TOOLBAR-SPEC §4 (`[70 %] [−] [===▮===] [+]`) в 0.3 не
   делается: группа свойств обязана держать 3 ячейки `ctlH` (иначе пилюля меняет ширину при смене
   инструмента). Остаются шаги 10 % и `%` как кнопка возврата к 100 %.

## 10. Открытые вопросы к владельцу

1. **Вторая подписная строка в пилюле** (§1.2). Карточка #22 и п.27 требуют буквально «в подписи
   группы вывода видно `есть несохранённые правки`», а групповая подпись сегодня стоит в той же
   строке, что подписи контролов, — в группе вывода она не влезает. Значит высота ячейки растёт на
   32 px при 175 % (пилюля 110 → 142 px), нужная высота окна — 227 + img.h → 259 + img.h; при
   снимке во весь экран окно и так упирается в `scrH − 8`, то есть **32 px нижней кромки снимка
   перестают быть видны**. Подтверждаете этот обмен (32 px снимка на читаемую подпись выводной
   группы), или индикатор переезжает в полосу статуса (тогда надо править формулировку п.27)?

2. **Неактивный «Сохранить» на снимке без правок** (§5.3). Требование есть в TOOLBAR-SPEC §2 и в
   карточке #22, следствие такое: снятый, но не правленный кадр нельзя сохранить кнопкой или
   `Ctrl+S` (остаётся «Копировать»), и пункты приёмки 23 и 24 нельзя проводить без предварительной
   правки (§9.5, §8). Подтверждаете именно это, или «Сохранить» активен, пока вывод вообще не
   сделан (тогда учёт `dirty_` в карточке #22 переформулируется)?

3. **Точная формулировка индикатора** (§5.2, §9.7): `есть несохранённые правки` — ≈ 230 px при
   19 px шрифте, ширина группы вывода 247 px. Если DirectWrite даст больше 247 px: укоротить до
   `правки не сохранены` (≈ 175 px, против буквы п.27) или добавить группе вывода третью строку
   (ещё +25 px высоты, см. вопрос 1)?
